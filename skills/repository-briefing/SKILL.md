# Repository Briefing

面向陌生或较大的代码仓库，先建立地图，再按问题读取证据。不要整仓逐文件读取，
不要把文件名、README 宣传语或模型常识当成已经验证的实现。

## 目标

交付一份可追溯的仓库导读，至少回答：

1. 项目解决什么问题；
2. 如何安装、配置与运行；
3. 主要模块如何协作；
4. 一条关键请求从入口到结果如何流转；
5. 测试、持久化、错误处理与安全边界在哪里；
6. 哪些结论已有代码证据，哪些仍是推断或待验证项。

## 工作流

### 1. 明确范围

- 确认分析对象是当前 Workspace，还是指定的 GitHub 仓库、分支、tag 或 commit。
- 结合用户问题确定深度：快速概览、模块讲解、执行链追踪、风险审查或架构文档。
- 远程仓库先确认仓库身份与 ref，遇到 API 限流、404 或私有仓库时如实说明。

### 2. 广度优先建立地图

先读取：

- 顶层目录；
- README、许可证和贡献说明；
- 依赖清单与构建配置；
- 启动入口、示例配置；
- 测试目录和 CI 配置。

输出一个临时模块地图，再决定下一批文件。不要因为目录很大就一次性读取所有文件。

### 3. 按证据深入

优先选取少量高价值文件：

- 程序入口与路由/命令入口；
- 核心编排或 Agent Loop；
- 数据模型、存储和上下文构建；
- Tool、Skill、Approval 等扩展边界；
- 一至两个代表性测试。

如果本 Skill 的资源目录中有检查清单，使用 `read_skill_resource` 分段读取。资源较长时
依据 `nextOffset` 继续，不要凭截断片段宣称“已完整读取”。

### 4. 追踪一条真实执行链

选择与用户目标最相关的一条路径，例如：

`用户输入 → Gateway/CLI → Runtime → LLM → Tool → Session Store → 输出`

每一步都标注对应文件、类或函数。找不到证据时写“待确认”，不要补写不存在的模块。

### 5. 验证

- 运行命令只能引用仓库中真实存在的文档或配置；不能把猜测的命令写成事实。
- 能安全运行测试时，使用 Tool 执行最小验证并记录结果。
- 只有成功的 Tool Result 才能证明读取、测试或生成动作已经完成。
- 对超长文件采用定位关键词、分段读取和交叉验证，不用单个截断片段下结论。

### 6. 交付

最终使用清晰的中文 Markdown：

1. 一句话定位；
2. 快速启动；
3. 模块结构；
4. 核心数据结构；
5. 关键执行链；
6. 测试与可靠性；
7. 风险、未知项与下一步；
8. 证据索引（文件路径或 GitHub URL）。

将“已验证事实”“合理推断”“尚未验证”明确区分。用户只需要快速介绍时压缩篇幅，
但保留关键证据路径。
